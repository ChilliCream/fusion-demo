# Subgraph (Source Schema)

These rules apply when the server is a source schema in a composite schema setup — its schema is composed with other source schemas behind a gateway. Everything else in this skill applies unchanged; this reference holds the subgraph-specific practices on top.

How to tell you are in a subgraph — either signal is enough:

- the builder chain calls `.AddSourceSchemaDefaults()`, or
- the project contains a source-schema settings file: `schema-settings.json`, holding the source schema's registration for composition — its `name`, transport (the http URL the gateway calls), and per-environment endpoint URLs. The file is generated by the tooling — never create or edit it yourself; its presence is purely a detection marker:

  ```json
  {
    "name": "products-api",
    "transports": {
      "http": { "clientName": "fusion", "url": "{{API_URL}}" }
    },
    "environments": {
      "aspire": { "API_URL": "http://localhost:5110/graphql" },
      "prod": { "API_URL": "https://api.example.com" }
    }
  }
  ```

## Becoming a source schema

Name the schema and add the source schema defaults:

```csharp
builder
    .AddGraphQL(Env.ProductsApi)
    .AddSourceSchemaDefaults()
```

- The schema name identifies this source schema within the composite setup.
- `AddSourceSchemaDefaults()` applies the subgraph behavior — among other things it enables variable and request batching by default, which the gateway relies on when it resolves entities through your lookups.

## Lookups

`[Lookup]` marks a field as a fetcher for an entity by its stable key. Put it on every root `byId` field — the gateway uses lookup fields to resolve entities across source schemas.

**The service owns the entity → the lookup fetches through a DataLoader.** The gateway batches lookup calls hard (alias batching, variable batching), so the field must coalesce into single database roundtrips — see [dataloaders.md](dataloaders.md):

```csharp
[QueryType]
internal static partial class RecommendationQueries
{
    [Lookup]
    public static async Task<Recommendation?> GetRecommendationByIdAsync(
        int id,
        QueryContext<Recommendation> query,
        RecommendationByIdDataLoader recommendationById,
        CancellationToken cancellationToken)
        => await recommendationById.With(query).LoadAsync(id, cancellationToken);
}
```

**The entity is constructible from its key alone → no fetch at all.** A reference to an entity another source schema owns needs only its key:

```csharp
[QueryType]
public static partial class ProductQueries
{
    [Lookup]
    public static Product GetProductById([ID<Product>] int id)
        => new(id);
}
```

`[ID<Product>]` types the raw key as `Product`'s global ID. The field is synchronous and non-null — there is nothing to fetch and nothing that can be missing.

Lookup rules:

- Every root `byId` field carries `[Lookup]`.
- Nullability follows the shape: a fetched lookup is nullable (`Recommendation?` with `LoadAsync` — the key may not exist); a constructed reference is non-null (nothing can be missing).
- The lookup's key argument is the entity's stable key — the same key the order tail and DataLoader dictionaries are built on.

## Cost enforcement is the gateway's job

```csharp
builder.ModifyCostOptions(x => x.EnforceCostLimits = false);
```

The subgraph still adds the cost annotations to its schema — composition and the gateway need them — but it does not enforce the limits itself. Enforcement is up to the gateway. A standalone server keeps enforcement on.

## Node field as lookup

```csharp
builder.AddGlobalObjectIdentification(o => o.MarkNodeFieldAsLookup = true);
```

The relay `node` field acts as a lookup, so the gateway can resolve any node-implementing entity through it. This is part of the default settings (see [server-setup.md](server-setup.md)).
